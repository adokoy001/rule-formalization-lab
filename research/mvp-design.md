# 最初の試作品の設計案

調査日: 2026-09-14
位置づけ: 調査時点の初期提案。実装済みの仕様ではない。

**更新:** ユーザーの自前化方針を反映した[最新の開発計画](../planning/README.md)を優先する。本書のZ3中心の案は、比較用の初期提案として保存している。

## 1. 最初に作るもの

仮称は「ルールのデバッガ」。日本語の規約と形式化したルールを並べ、問題の起きる具体的な条件と根拠条文を表示する。

初回の対象は、会員資格・料金・申請期限を定める架空の規約20条程度。年齢、金額、日数、真偽値に対象を絞る。例外の優先関係は明記されたものだけを扱う。

まず手で確認した形式モデルから検査器を作り、その後にLLMによる形式化案の作成を追加する。これにより、検査器の誤りと原文の読み違いを別々に評価できる。

## 2. 入力から結果まで

```mermaid
flowchart LR
    A["原文・条文ID・版"] --> B["形式化案と未解決の解釈"]
    B --> C["人による対応確認"]
    C --> D["型のあるルール表現"]
    D --> E["例外・適用時点の解決"]
    E --> F["検査用の論理式"]
    F --> G["SMTによる探索"]
    G --> H["条件の具体例・関係条文"]
    H --> C
```

画面は「原文」「ルール表」「検査結果」の3領域を基本にする。結果から該当条文へ戻り、年齢や期限を変えて再検査できると、形式化を学ぶ趣味としても扱いやすい。

## 3. 検査を区別する

| 検査 | 探すもの | 結果の例 |
|---|---|---|
| 結論の衝突 | 同じ対象・行為・時点に、両立しない結論を与えるルール | 18歳では資格ありと資格なしが同時に導かれる |
| 条件の到達不能 | 業務上可能な入力で、適用条件を満たせないルール | 年齢20歳以上かつ18歳未満 |
| 適用漏れ | 全員の扱いを決めると宣言した対象範囲のうち、どのルールも適用されない部分 | 18歳の料金が定義されない |
| 数値・期限の不整合 | 同時に満たせない値や日程 | 支払日は契約から10日以内、かつ15日以降 |
| 優先関係の不備 | 優先順位の循環や未解決の衝突 | 第2条が第3条に優先し、第3条が第2条に優先 |
| 改定の影響 | 旧版と新版で結論が変わる入力 | 19歳の会費だけが変わる |

適用漏れを問題とするのは「対象範囲のすべてに結論が必要」という仕様がある場合に限る。循環する参照も、それだけで論理矛盾とは限らない。禁止されている行為が実際に行われたことは違反であり、規則同士の不整合とは区別する。

## 4. 小さな例で検査の意味を確かめる

以下は本プロジェクト用の架空例であり、実在の法律の説明ではない。

- R1: 18歳以上の人は、会員資格を持つ。
- R2: 20歳未満の人は、会員資格を持たない。
- 仮定: 年齢は0〜120の整数。同じ人・同じ日について判定する。条文間の優先関係は未指定。

年齢を `a`、会員資格の有無を `E` と置く。

```text
D  := 0 ≤ a ≤ 120
R1 := a ≥ 18 ⇒ E
R2 := a < 20 ⇒ ¬E
```

ここで `D ∧ R1 ∧ R2` を一度解いて SAT になっても、「すべての年齢で衝突しない」とは言えない。例えば `a = 30, E = true` は全体を満たすが、18歳・19歳では両方の結論が要求される。

この2ルールの場合は、相反する結論の適用条件が重なるかを調べる。

```text
D ∧ (a ≥ 18) ∧ (a < 20)
```

満たす年齢は18歳と19歳。次に `a = 18` を固定してR1とR2を入れると、`E ∧ ¬E` となり UNSAT になる。このとき関係するルールと入力条件を、説明の根拠として返す。

一般の複数段推論では、2ルールずつの比較だけで十分とは限らない。初期版は直接の結論衝突に範囲を絞り、推論連鎖や3つ以上の制約の組合せは、検査の種類を追加して扱う。

R2がR1の例外であると原文・解釈で明示された場合、R1の有効条件を `a ≥ 18 ∧ ¬(a < 20)` にする設計が考えられる。その優先関係を勝手に補完して、衝突を消してはいけない。

## 5. 結果の読み方

- 衝突する状況を探す式が SAT: モデル内で衝突を起こす入力の具体例が見つかった。
- 特定状況のルール集合が UNSAT: その仮定と状況では、要求を同時に満たせない。
- 対象の衝突探索が UNSAT: 指定した表現・範囲・仮定では、その種類の反例がない。
- UNKNOWN / タイムアウト: 結論を出せなかった。検査合格として扱わない。

SAT/UNSATの意味は、何を問い合わせたかによって変わる。原文、形式モデル、探索式、結果を組で保存する。

Z3は矛盾に関係する制約の部分集合を返す機能を持つ。ただし通常の unsat core は最小とは限らない。包含関係で極小の集合と、要素数が最少の集合も別である。最初は「矛盾に関係する条文」と表示し、最小性を保証したような表現は避ける。[Z3公式解説](https://z3prover.github.io/papers/programmingz3.html)

## 6. 中間表現に保存する情報

| 要素 | 内容 |
|---|---|
| 原文との対応 | 文書ID、条文ID、原文範囲、URL、取得日、原文の版 |
| 対象と語彙 | 人・組織・行為・属性の型と、用語の同一性 |
| 条件と結論 | 適用条件、導かれる値や資格 |
| 規範の種類 | 義務・禁止・明示的許可。実際に起きた事実とは別に保持 |
| 例外 | 優先する条文ID、その解釈の根拠 |
| 時間 | 施行期間、事実の発生日、判定基準日、期限 |
| 仮定 | 未定義の語、外部に必要な事実、採用した解釈 |
| 確認状態 | 自動生成案、人が確認済み、未解決 |

初期版の検査対象は資格・料金・日付などの決定ルールとする。義務を単なる実際の行為の真偽値へ潰すと「すべき」と「した」が混同される。義務論理を導入する段階で、義務・許可・違反後の義務の意味を別に定義する。

## 7. 技術選択の提案

最初は Python と Z3 を候補とする。整数・金額・日数の制約と具体例の抽出が、今回の検査対象に合うためである。契約を構造化した表現からSMTへ変換する ContractCheck は、近い構成の先行例になる。[原著論文](https://link.springer.com/article/10.1007/s10506-025-09456-8)

使用する論理の断片を明示し、当初は量化子なしの線形整数制約を中心にする。金額は最小通貨単位の整数、日付は定義した起点からの日数などで表現する。丸め、暦日と営業日、年齢の基準日はそれぞれ仕様として決める。

例外中心の実行可能な法制度の記述を深める場合はCatala、説明つきの規則推論ならBlawx/s(CASP)、義務の意味論そのものを研究したい場合はI/O logicやIsabelle/HOL系を比較する。これらを最初から全部接続する必要はない。

LLMには、原文の区切り、語彙の候補、形式化案、複数の解釈案を作らせる。検査結果の根拠はソルバーの出力から組み立てる。型検査に通ったことも、原文の意味が保存された証明にはならない。

## 8. 小さな評価セット

まず30件程度を目安に、正解つきの架空規約を作る。以下のケースと、誤検出してはいけない対照例を用意する。

1. 年齢境界の衝突と、境界が正しく分かれた例。
2. 明示的な例外で解決する衝突と、優先関係のない衝突。
3. 期限の衝突と、日付がちょうど境界にある例。
4. 全対象を覆う規約と、扱いのない対象が残る規約。
5. 原文に定義のない用語や外部参照がある例。
6. 同じ結論になる旧版・新版と、特定の入力だけ結果が変わる例。
7. 義務違反の事実があるが、規則同士は矛盾していない例。
8. 語順や言い換えだけが違う同義文、複数の解釈が成立する文。

評価は、形式化の正確さ、検査の適合率・再現率、示した反例の再現性、根拠条文の対応、未解決と返すべき問題を無理に断定しないことを分けて測る。

## 9. 実装する順序

1. 架空規約と対応する手作業のルール表を作る。
2. 直接の衝突・条件の到達不能・適用漏れを検査するCLIを作る。
3. 反例と関係条文を原文に戻す小さな画面を作る。
4. 明示された優先順位と日付の版管理を追加する。
5. LLMによる形式化案と、人が修正する画面を追加する。
6. 公開された日本語の法令工学資料と照合する小さなケースへ進む。

最初の完成条件は、「自然文・確認済みルール表・反例・根拠条文の対応が追えて、意図的に入れた欠陥を再現できる」こと。現行法全体の正しさや、任意の自然文からの完全な自動形式化は初回の評価対象にしない。
