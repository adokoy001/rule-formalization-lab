# A. 完全自前の形式モデル検証ソフト

状態: 全体の設計案 v0.1。2026-09-15に決定値だけの限定profile [finite-decisions/1](../docs/kernel-v0.1.md)と[段階別到達可能性診断](../docs/staged-reachability-v0.1.md)、2026-09-16に時間なしの義務・禁止・明示的許可を扱う別profile [finite-norms/1](../docs/normative-kernel-v0.1.md)を実装した。以下は将来機能を含む設計であり、実装範囲・テストは[基礎検証](../docs/verification-2026-09-15.md)、[T03.1検証](../docs/verification-t03.1-2026-09-15.md)、[T08検証](../docs/verification-t08-2026-09-16.md)を参照する。

## A1. 実装境界と信頼対象

本番で既成SAT/SMT/論理プログラミングエンジンを呼ばない。当初はRustで検査・探索・証拠処理、Pythonで参照評価器を作る案だった。最初のv0.1はPython標準ライブラリだけの探索器と別実装のcheckerに絞った。Rust化は将来の選択肢として残す。

自前であることは無欠陥の根拠にはならない。最小の証拠検査器、入力の解釈、数値演算、処理系、実行環境に信頼が残る。各リリースには、次を分けた保証台帳を付ける。

- 数学的に記述しレビューした意味論。
- 証明義務と、その証明の状態。
- 個別の結果に添え、検査を通った証拠。
- テストで確認した範囲。
- 信頼対象として残る実装と環境。

「テストに全件合格」と「健全性が証明された」を別の状態にする。

Aは手書きのCoreも単体で受け取れる。`origin_kind = authored_core`では元Core自体を出典として保存し、自然文との意味対応の保証は持たない。Bから受け取る`origin_kind = interpreted_source`では、原文・承認スナップショット・変換来歴を必須にする。どちらも型・意味・証拠の検査は省略しない。

## A2. 有限Coreの型と式

Core profileは `finite-rules/1` とする。

| 構成 | v1の規則 |
|---|---|
| Bool | 完全な一つの状況では真か偽。未入力は別途、複数の補完状況として扱う |
| Enum | 非空の明示された有限型。値に永続IDを付ける |
| BoundedInt | 上下限付き整数。意味は数学的整数。桁あふれや剰余による循環を認めない |
| Money / Duration / DateIndex | 単位や暦プロファイルを持つ整数。暗黙の相互変換なし |
| 式 | 定数、変数、型付き比較、and/or/not、if-then-else、有限量化 |
| 算術 | 最初は加減算・定数倍。除算・丸めは別の演算仕様とテストを追加してから扱う |
| 定義 | 入力と先行する純粋定義だけを参照するDAG。意味は等式 |
| 規則の条件 | 入力と純粋定義だけを参照。他の規範出力・決定結果はv1で参照しない |
| 規則の帰結 | 決定値、義務、禁止、明示的許可のいずれか |
| 量化 | 宣言した有限型全体へ展開。暗黙の無限対象や自由変数は禁止 |

定義 `eligible := condition` と、十分条件だけを述べる規則 `condition → eligible` を別ノードにする。後者から逆や裏を自動生成しない。

Rust実装では検査付き整数演算を使い、中間値まで静的に表現可能か確認する。表現上限を超える式はモデル受理の段階で拒否する。数学的な範囲を黙って縮めたり、整数を浮動小数へ変換したりしない。二進符号化を導入する場合もこの意味は変えない。

## A3. 状況、出力、行動列を分ける

- `c`: 対象者、属性、基準日などの完全な入力状況。
- `D(c)`: 宣言された対象範囲と確認済みの入力・背景条件。
- `τ`: 有限時点における行動列。
- `T(c,τ)`: 物理的・業務的に可能な行動列の条件。
- `Results(c)`: 有効な規則から得た決定値や規範の集合。

実装済みの`finite-norms/1`における`tau`は、時間順序を持たないBoolean行動割当である。この節で予定する有限イベント列、時刻、観測終了はT09の対象で、T08では未実装。

相反する決定値や規範は、その集合の中に両方残して検出する。衝突する状況を、入力制約で初めから除外してはならない。

観測した事実は肯定根拠・否定根拠を別に保持する。`both`の入力が対象の依存範囲にあれば `INPUT_INCONSISTENT`。根拠のない `neither` を偽へ変換しない。これは四値の情報状態の保存であり、四値の推論論理を実装済みという意味ではない。

部分的な入力からは、整合的な補完状況の集合 `Ω = {c | D(c)}` を作る。

- Ωが空なら `BASE_INCONSISTENT`。空虚な全称命題で合格させない。
- 全補完で成立、一部で成立、どこでも不成立を区別する。
- 原文の複数解釈は入力の未知とは分け、別の解釈スナップショットとして実行する。

## A4. 例外の意味論

`override(s,r)` は「有効なsが、指定されたrを無効化する」という明示的な関係。一般的な優先順位の推測を行わない。

```text
enabled(r,c) =
  guard(r,c) ∧ applicable_time(r,c)

effective(r,c) =
  enabled(r,c)
  ∧ ∧ { ¬effective(s,c) | override(s,r) }
```

打消しDAGの上位から評価する。辺の推移閉包を勝手に追加しない。

必須の意味論テスト:

1. 条件を満たさない例外は原則を消さない。
2. 比較できない二つの規則は、配列の順で勝者を決めない。
3. `R3 overrides R2`、`R2 overrides R1`で3つが適用可能なら、R3が有効、R2が無効、R1が再び有効になる。
4. 特定の人・期間だけの例外は、その範囲を保持する。点ごとの決定や全称的な禁止など、意味が保存される分割だけを許可する。`O(期間内に一度A)`を各時点の`O(A_t)`へ分割すると存在条件が全称条件へ変わるため禁止する。時間窓を持つ義務に対する一般的な部分期間overrideは、意味を別途定義できるまで未対応とする。
5. 循環は「法律が矛盾している」と断定せず、この意味論で未対応として拒否する。

規則の条件・純粋定義の依存グラフと、打消しグラフの両方を検査する。二つのグラフを別々に持つだけでは不十分なので、許可した参照種別も検査し、v1で禁止する出力から条件への参照を弾く。

この意味論は本プロジェクトの限定した選択であり、一般的なDefeasible Logic全体ではない。

## A5. 義務、禁止、許可、違反

行為が発生した事実と、行為が要求されたことを別にする。

- `O(φ)`: 履行条件φを満たす義務。
- `F(φ)`: φを禁止する。遵守条件は¬φ。
- `P_explicit(φ)`: 明示的な許可の記録。φを実際に行う義務にはしない。
- `P_weak(φ)`: 閉じた規則集合と固定状況で、指定した禁止がないという照会。原文中の独立した許可や¬O(φ)と同一視しない。

有効な義務・禁止だけから遵守条件 `H(c,τ)` を作る。明示的許可は無条件に禁止を取り消さず、必要なら根拠付きのoverrideを別に置く。許可の行使可能性は個別に検査し、複数の許可を全部同時に行使する必要はない。

```text
Compliant(c,τ) := T(c,τ) ∧ H(c,τ)

PermissionUsable(c,φ) :=
  ∃τ. Compliant(c,τ) ∧ φ(c,τ)
```

許可と禁止が同じ行為について有効なら、許可との両立性の問題として報告する。許可があるだけで、実際の行動列を不整合にしない。

時間窓について:

- 「期間内に一度」は存在量化。
- 「期間中は禁止」は全称量化。
- 義務期間と禁止期間が一部重なるだけでは、履行不能とは限らない。禁止期間の外で履行できる可能性を調べる。
- `O(A ∨ B)`と`F(A)`は、Bを行えるなら両立する。
- 施行期間、義務発生時点、行為時点、期限、観測終了を分ける。
- 観測終了が期限より前なら、将来の不履行を確定しない。`OBSERVATION_INCOMPLETE`等で表示する。

違反後の救済義務は拡張段階。一次違反と救済の履行の両方を履歴に残す。

## A6. 検査命題と量化

| 検査 | 正確な問い |
|---|---|
| 決定衝突 | ∃c. D(c)かつ同じ決定キーに異なる値を出す有効規則がある |
| 条件の到達可能性 | ∃c. D(c) ∧ enabled(r,c) |
| 有効な適用の到達可能性 | ∃c. D(c) ∧ effective(r,c) |
| 適用漏れ | 完全な定義を要求した対象で、いずれの有効規則も結果を与えないcがある |
| 固定状況の履行可能性 | ∃τ. T(c,τ) ∧ H(c,τ) |
| 許可の行使可能性 | ∃τ. T(c,τ) ∧ H(c,τ) ∧ φ(c,τ) |
| 違反 | 観測の確定範囲で履行条件が破られているか |
| 改定差分 | 共通の入力範囲で、旧版と新版の決定・衝突・未定義等の状態が異なるか |

**どこかの状況で全義務を守れないか**は、

```text
∃c. D(c) ∧ ¬∃τ. (T(c,τ) ∧ H(c,τ))
```

という量化の交替を持つ。cとτを両方変数として、一度SATを解くだけでは答えられない。

v1ではcを有限列挙し、各cについて行動列の存在を自前探索する。最初に `∃τ.T(c,τ)` を確認し、元から行動列が存在しなければ `BACKGROUND_TRACE_IMPOSSIBLE` として、規範に原因がある場合と分ける。該当状況を無言で探索から捨てない。

規範による履行不能の反例は、状況c、背景だけなら可能な行動例、遵守行動が存在しない証拠を持つ。すべての状況で履行可能だと示す場合は、全状況の被覆と、それぞれの履行例が必要になる。

適用漏れは対象全体を定義するという要求がある場合だけ検査する。到達不能と、例外により常に無効になることも別の検査にする。

限定`finite-decisions/1`ではT03.1として、宣言Cartesian積上のguard `G`、guard+facts `GF`、guard+constraints `GC`、enabled `E`、override後effective `V`を全数で集計する別証拠形式を実装した。ホスト管理のscope期待との照合はこの段階値とは別に記録する。これは固定有限domainの診断であり、一般の式の矛盾理由、原文に対する正しいscope、法的適用範囲を自動判定しない。

## A7. 二段階で作る探索器と証拠

### 先に作る: 元のCoreを直接評価する完全列挙器

小さな有限モデルを全列挙する。条件、例外、帰結、行動列の意味を仕様どおり直接評価する。原文対応を失わない。

初期の「反例なし」の証拠は、**Core変数の有限領域を覆う探索木**とする。独立checkerは次を確認する。

- 子の領域が親の領域を漏れなく覆う。
- 未処理の枝がない。
- 葉が完全割当であり、元Coreで反例条件が成立しない。
- 型、入力条件、query、モデルのハッシュが一致する。

初期は高度な枝刈りを避ける。部分割当で葉を閉じる最適化には、別の健全な閉鎖規則と証拠が必要。この方式は遅く証拠も大きいが、CNF変換だけを正しく検査して原Coreを取り違える穴を避けやすい。

### 次に作る: 自前DPLLとCNF変換

1. 有限型をBooleanへ展開する。初期はone-hotと「ちょうど一つ」の制約。
2. 定義・比較・条件・検査命題を、固定した変換規則でCNFへ落とす。
3. 自前の単位伝播と二分岐で探索する。
4. SATなら割当、UNSATなら根拠節付きの完全なDPLL証明木を返す。

SATの割当はCNFと元Coreの両方で再評価する。UNSATの木では、両分岐の存在、単位伝播の根拠、葉で偽になる節をcheckerが検査する。

**UNSAT(CNF)の証拠だけでは、元Coreの正しさにならない。** 各型・演算・補助変数導入について、元の検査式の成立とCNFの充足可能性の対応を確認する変換証跡を付ける。この変換検査が未実装の段階では、高速経路の結果を正式なCoreの証明へ昇格させず、直接列挙経路で検査する。

最後にCDCL、学習節、watched literals、二進整数を追加する。学習節はまずヒント付きRUPで検査し、節削除・RAT・高度な前処理は後回し。RUP部分だけを実装した段階で、LRAT全仕様対応とは呼ばない。[LRATの原著](https://arxiv.org/abs/1612.02353)

## A8. 証明義務

| ID | 必要な主張 |
|---|---|
| P01 | 受理された型付き式の評価が、一意で全域的である |
| P02 | 定義DAGとoverride DAGの評価が停止し、順序の取り方で結果が変わらない |
| P03 | 参照列挙が宣言された入力・行動の全領域を覆う |
| P04 | 有限展開・CNF変換で、元の検査命題と充足可能性が対応する |
| P05 | checkerが受理した反例は、元Coreの命題を満たす |
| P06 | checkerが受理した非存在の証拠は、元Coreの対象領域全体を覆う |
| P07 | 無制限の資源を仮定した有限参照探索が、受理言語内で答えを返す |
| P08 | 打切り・不正証拠・未対応を確定結果へ変換しない |

仕様上の証明、実装への対応、テストを別々に記録する。小さな全数検査だけでP01〜P08をすべて数学的に証明したとは扱わない。

## A9. 説明・core・修復

初期版は反例と関係規則を表示する。UNSAT証拠とunsat coreは別物。

極小の原因集合を提供する場合は、背景Bを固定して以下を付ける。

1. `B ∧ K`がUNSATである証拠。
2. 各kについて、`B ∧ (K−{k})`がSATである割当。

これは包含関係で極小であり、要素数が最少という意味ではない。

さらに例外があると、原文の規則を削除した際に別の規則が復活する。そのためKは、**固定した状況・背景・例外解決後の正規化制約集合**に対して定義する。原文条文へのリンクは由来であり、「この条文だけ残しても必ず矛盾する」とは自動で言わない。条文の削除や修正案は、例外処理から再検査する。

## A10. 結果APIと再現用の検査束

結果を単一のvalidフラグにしない。

```text
query_kind
query_hash
semantics_profile
source_manifest_hash
interpretation_snapshot_hash
core_hash
scope_manifest
input_assumptions
finding = present | absent | undetermined
status
certificate_status
certificate_hash
witness / explanation_links
engine_version / checker_version / transformation_version
resource_limits / statistics
```

主なstatus:

- `WITNESS_VERIFIED`: queryを満たす具体例が元Coreで確認できた。
- `NO_WITNESS_IN_SCOPE_VERIFIED`: queryを満たす例が範囲内にない証拠が確認できた。
- `BASE_INCONSISTENT` / `INPUT_INCONSISTENT`: 背景または入力の不整合。
- `BACKGROUND_TRACE_IMPOSSIBLE`: 規範を課す前から行動が不可能。
- `MODEL_INCOMPLETE` / `UNSUPPORTED`: 解釈・表現・範囲の問題。
- `LIMIT_REACHED`: 探索、証拠生成、証拠検査のいずれかが打切り。
- `CERTIFICATE_INVALID`: 証拠が対象と合わない、または不正。
- `OBSERVATION_INCOMPLETE`: 実行履歴が判定に足りない。

`WITNESS`が衝突なのか履行例なのかはquery_kindで決まる。queryの意味を結果とセットにし、ラベルだけで解釈しない。

## A11. 初期の具体的な検査

- Booleanは3変数、各節は1〜2リテラル、重複・恒真節なし、節集合は最大3節としたCNFを全数生成する。18種類の節からなる988個の集合について、各8割当の素朴評価と比較する。
- 空節を含むUNSAT、空CNF、変数が未使用の場合は別fixtureで検査する。
- 3つ以上で初めて生じる不整合、例外復活、同順位衝突、未知入力を含むモデルを追加する。
- 証拠の枝欠落、節ID改ざん、単位伝播偽造、モデル差替え、未対応版を拒否する。
- 原文の「以下」を「未満」へ変える翻訳変異と、Coreの≤を<へ変えるコンパイラ変異を別に検査する。
- 元Coreの意味、参照列挙、自前SAT、独立checkerの結果を照合する。

検査の具体件数はこの小さな集合についてのみ保証する。任意の3変数論理式を全て検査したという意味ではない。
